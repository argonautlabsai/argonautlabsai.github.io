DEEPSEEK V4.1 FLASH Q4 / 27 SEPTEMBER 2026

Start the expert reads
before the GPU is done.

20.30 to 22.74 steady tok/s at 512 prompt / 512 generated, +12.0% over our published 21 September engine on the same three drives, with byte-identical output on every arm.

What was tested

DeepSeek V4.1 Flash Q4, 518,596,067,328 bytes, SHA-256 a5e2e2c3ada4b2e9…. M5 Max, 128 GB, the internal SSD plus two Thunderbolt 5 NVMe enclosures holding byte-identical verified copies, prefill reads split 10:5:5 and decode reads 10:6:6. Control: the binary built from our published tag v41-router-qualified-20260921 with its profile and 4,200 cached experts, the 20.375 tok/s champion of 21 September. Candidate: the same source tree plus three opt-in engine paths and 4,600 cached experts, profile v41-stack-20260927. Same drives, same model copies, same prompt, same session. This page is not a comparison with upstream ds4; the 15 September page has that.

Where a token's 49.6 ms went

Before this session the champion spent, per generated token, about 34 ms inside the GPU command buffers, 13.1 expert-cache misses at about 0.8 ms each, and around 5 ms of fixed CPU work. The large matrix-vector kernels already ran at 69 to 100% of the roughly 570 GB/s memory roofline and the three drives were at their read ceiling for six experts a token, so the remaining software was in the seams: how soon the miss reads start after the router has chosen, how many experts stay resident, and about 1,300 small dispatches a token.

No build ran and no second engine process existed during any arm. Prompt processing is prefill tokens divided by prefill seconds; generation excludes prefill and startup; steady also excludes the first decode step.

Which change earns which number

Flag readback is most of it. The larger cache is the next third, and the three small items are under one percent each. The single screens sum to about 11.6%; the stack measured 12.0% and 12.6% as a whole, so the levers neither cancel nor compound much. The costs are real and small: prompt processing 44.95 → 44.02 tok/s (−2.1%) and a first decode step of 452 instead of 371 ms, both because the larger cache seeds more expert slabs after prefill. Decode drew about 3 W more.

What did not work

Caches of 4,750 and 4,900 experts exceeded the swap-growth guard on this 128 GB machine, with and without deferring the growth until the prefill staging pool is released. Turning the CPU keep-alive off on top of the stack measured −0.09%, inside the noise, so the setting stays. Memory-touching keep-alive kernels, read-pool spinning, completion polling, Q8 row tiling and SIMD-group variants, eighteen reader threads and pipeline pre-warming were each screened with interleaved pairs and rejected; the knobs remain in the source, off by default. Pre-warming experts, staging the release of the prefill pool, static buffer views and warming the slabs did not shorten the first decode step, which remains a separate target.

28 September follow-up: what four more hours bought

The next morning set out for another 10% and got 1.5%. Two opt-in changes qualified against the 27 September binary built from its tag, same session, same profile and cache, output identical on every arm: a post-MoE flush, which commits a layer's routed work as soon as it is encoded when that layer waited for expert reads so the GPU starts it while the CPU encodes the next layer, and an eviction pre-scan, which ranks cache victims while the CPU is idle on the router mailbox instead of scanning 4,600 entries on the critical path. Next-layer prediction, the only lever that could hide the expert-read waits, was re-tested through the flag-readback mailbox and lost in every form: top-2 prediction costs about 1.2 ms of GPU per token and buys 0.85 misses; reading only the predicted non-resident experts cuts misses by a third but the speculative reads share the drives with demand reads and displace resident experts. A token is now about 43 ms: 34 ms of kernels at 69 to 100% of the memory roofline, 5 to 6 ms of exposed read waits, 3 to 5 ms of command-buffer boundaries, 2 ms of CPU. The next real step is a GPU-driven expert gather that removes the per-layer command buffers, which is a multi-day change.

Limits

One machine, one model, one prompt at two generated lengths. The stack qualification is against our own published binary in the same session; the ladder is against the pinned upstream base of this fork, not current upstream ds4, and two runs per configuration give an observed range rather than a confidence interval. The 4,600-expert cache needs the headroom of a 128 GB machine. Keep-alive remains enabled and raises power draw. Identical output on every arm is regression evidence, not model-quality validation, and chat or server throughput was not measured.
