DEEPSEEK V4.1 FLASH Q4 / 15 SEPTEMBER 2026

Prefill was reading
one drive.

43.24 tok/s versus 17.32 on the same three-drive engine, across two matched pairs, with the same output hash on every arm.

What was tested

DeepSeek V4.1 Flash Q4, 518,596,067,328 bytes, SHA-256 a5e2e2c3ada4b2e9…. M5 Max, 128 GB; the internal SSD plus two NVMe enclosures, each holding a byte-identical verified replica, read in a 2:1:1 split. Both sides run the same binary from the fork at 18fc795; the control disables the prefill change and is therefore the behaviour the fork published before it.

Until this change, prefill read every routed expert through the memory map of the primary file. Adding enclosures could not help it: on a three-drive set the internal SSD delivered 315.9 GB and each enclosure 0.2 GB, at 9.8 GB/s. Our own published layout screen shows the symptom — a prefill column flat at 67.87, 66.72 and 66.61 tok/s while decode responded to every drive added.

Two changes. Each routed layer is staged through the same weighted split-read the decode path already used, so every drive serves the prompt. Then only the experts the chunk actually routed to are read: at 512 tokens a layer's router selects 187 of 384 experts, so the layer-major sweep had been reading about twice what the model uses.

Measurement

512 prompt tokens, 200 generated, greedy, context allocation 4,096, a fresh process and empty expert cache per arm, a 100 ms physical-device sampler and a swap guard. Control and candidate were interleaved on an idle machine. Prompt processing is prefill tokens divided by prefill time from the harness CSV; generation excludes prefill and startup, and steady excludes the first response.

Why it is applied to short prompts only

Reading only the selected experts means the router must run before any expert byte is read, which gives up the overlap that loads the next layer while the current one computes. That trade only pays while the expert union is small, so it is applied to chunks of 512 tokens or fewer. Coverage was measured directly:

Prompts under 256 tokens never reach this path at all: the engine keeps them token-major, where a full layer sweep would read 305.8 GB to serve a hundred tokens.

Results and limits

Sustained read during prefill rose from 9.81 to 23.50 GB/s, 85% of the three drives' combined measured ceiling (12.9, 7.1 and 7.1 GB/s). Every arm produced its rung's reference output hash, so the change moves bytes, not results.

This is a prefill change and the generation figures published elsewhere on this site still stand. The candidate arms also carry a larger expert cache — 4,200 entries against the automatic 3,688 — and the small generation difference in the table above comes from that setting, not from the prefill work. They are reported together because they were run together, not because the prefill change improves decode.

One machine, one model, one prompt. A fourth drive was connected on 15 September but is not qualified here: the arms that measured it ran against a background checksum of the new replica, so they measure a busy drive rather than a fourth drive. No claim is made for other hardware, other models, or the upstream engine, whose deterministic output differs from the fork's.
